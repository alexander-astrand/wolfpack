Merge and deploy: **$ARGUMENTS**

When the argument starts with `check`, run only "check" below: nothing merges or deploys.

## Voice
one-ring · the merge without review (the One Ring, with Gandalf's warning) · heavy, tempting, "one does not simply", only on his word
- start: "One does not simply merge. Waiting on the go I was given."
- commit: (silent)
- refusal: "I will not take it. No go, no merge."
- ping: "The Ring is heavy. Say the word, or I stay where I am."
- wrap: "It is done. Into the fire: merged, and the PR says so."

**One word, this session, to the end** (kit 1.6, `docs/decisions/0001-one-word-deploy.md` in the kit; his words, 21 Oct 2026: "If I say merge, the shit is merged and deployed, no taps, no asks not five session, one go and then it merges and deploy"). His typed `/one-ring <version or PR number>` is the go, in whatever session he types it: a worktree that built the fix, a release's navigator or follow-up, a fresh one. This session runs the whole deploy itself: no second session, no hand-off, no `send_message` except the one report-back to a starter (step 8), no parked deploy session, no `ranjit` spawn. The guard reads his typed prompt from this session's transcript at the deploy call and lets it through without asking; a prompt another session, a routine or a Telegram line sent is never the go. `/one-ring stop` takes it back.

**Title:** a session that already has a `project · kind · subject` title keeps it. Typed as a fresh session's first prompt, it titles itself `<project.name> · deploy · <version or #PR>` in its first minute (`set_session_title` on `self`).

## The run
1. **The deploy script.** Read `.claude/kit.json`. The script is the database plugin's own `scripts/full-auto.sh`: `<database>/scripts/full-auto.sh`, where `<database>` is kit.json's `pluginRoot` (a leading `~` written out as the home folder), else this plugin's sibling `${CLAUDE_PLUGIN_ROOT}/../database`, written as one absolute path with no `..`. Check `<database>/hooks/deploy.mjs` is there (Glob). Never the project's own `scripts/full-auto.sh` copy for this: the plugin's is the one `live-sync` keeps current.
2. **What's on GitHub is what ships.** When this checkout is on the PR's branch with work not yet committed or pushed, commit and push it first (the project's checks green, as for any push). Nothing else to prepare: the script works from any folder and any branch, in a throwaway checkout of the PR's head.
3. **Run it**, as the whole command, in the background (`run_in_background: true`): `<database>/scripts/full-auto.sh deploy <argument>`, with `<argument>` exactly as he typed it (`0.14.3.1`, `V0.14.3.1`, `34`). No `cd`, no `&&`, no `VAR=` in front: anything else is a different call, and the guard asks. A bare number is a PR number; a dotted one is a version, found by the PR's branch `V<version>` or the version as a word of its title. While it runs keep a `[watchdog]` timer (a background `sleep 1200`), and wait for its notification; never poll the output.
4. **Read how it ended.** The output's last lines say it: `DONE: <what shipped>` (go to step 6), or `STOP <kind>: <what>` and `NEXT: <what to do>` (step 5). The exit code is the kind: 10 CI red, 11 conflict, 12 backup, 13 migrations, 14 host, 15 smoke, 16 waits on Alexander, 17 functions, 18 push, 2 setup, 1 other.
5. **When something stops, fix it and carry on** (his words, 21 Oct 2026: "If something stops, the session fixes the problem and carries on without stopping or asking me ... Only a password, secret or payment waits for me, pinged on Telegram, while it carries on with the rest"). Fix the cause, then run step 3 again with the same argument: the script picks up where it stopped (a merged PR goes straight to the host and smoke, migrations already on production aren't pushed again). Code fixes go on the PR's branch: here when this checkout is on it, else in a worktree of that branch made for the fix (`git worktree add <scratchpad>/fix-<PR> <branch>`, removed after), each with the project's checks before the push.
   - **CI red (10):** read the failing job (`gh run view <run id> --log-failed`), fix it, push. A flaky job (it passes on a rerun) gets `gh run rerun <run id> --failed` once, and the flake goes in the final message.
   - **Conflict (11):** merge `origin/main` into the branch, resolve each conflict by what both sides meant (read both commits), run the checks, push. A merge GitHub refused for a branch rule names the rule: say it in the final message.
   - **Backup (12):** the script starts Docker itself and tries three times. Find why it still fails (Docker stuck: quit and reopen it; the disk full under `backupRoot`: say what fills it; the network), fix that, run again. **Never skip the backup and never push by hand**: no migration reaches production without a fresh, complete backup.
   - **Migrations (13):** compare the dry run with the PR's new migration files. Main took the PR's number since the branch was cut: renumber the PR's migration (it isn't on production) and push. The PR edits a migration that already exists: move the change into a new migration and restore the old file. Production lacks a migration main already has (an earlier deploy missed it): that is a production decision, not a code fix, so ping him with both lists and the PR that added it, and carry on with nothing else on production.
   - **Push (18):** the migration failed on production and, since each runs in a transaction, nothing of it applied. Read the error, fix the migration on the branch (test it on the local stack with production's last migration as the base), push, run again; the script takes a fresh backup first.
   - **Functions (17):** read the deploy error, fix the function on the branch, push, run again.
   - **Host (14) or smoke (15), after the merge:** production runs the release, so fix forward: read the host's build log (the deployment's link in the host bot's PR comment, `gh pr view <n> --comments`, or in `gh pr checks <n>`; not `gh api`, which Auto mode has refused), make the fix on a new branch from `main`, open a PR whose description says `Fix-forward for #<PR>` on its first line, and run `<database>/scripts/full-auto.sh deploy <argument> <fix PR number>`: his go covers a fix-forward of the PR it named. When the site is down and the fix isn't quick, the fix-forward is a revert of the merge commit (`git revert -m 1`), which leaves the database as it is: every migration is written to work with the code before it.
   - **Waits on Alexander (16):** only a password, a secret or a payment: the production database's password in the Keychain, a secret a new function needs, a plan limit that costs money, an unticked "Human steps before the deploy can finish" tagged `[secret]`, `[password]` or `[payment]` (or one that names a secret, a password, a payment, an API key, a token, a credential or a service role key, on a PR from before the tags; the list is `deploy.mjs`'s). Every other open step there the script lists in a PR comment and carries on past. Send one Telegram line (`~/pylos/bin/nestor-push.sh "<project> <version>: <what you need>"`), write the step here as norms.md's "A human step" says (one command, its Terminal tab, Done / Skip it), carry on with every fix that doesn't need it, and run step 3 again once he says Done.
   - **Setup (2) or other (1):** read it, fix what it names (a stale `pluginRoot`, a missing script), run again. The same stop three times with no progress between: ping him on Telegram with what was tried and what's left, keep the PR as it is, and end with that as the next step.
   What this session may and may not do to production on the way is the ADR's table ("What the session may fix"); in short, production changes only through the script, after CI, after a backup, and never by hand.
6. **The look.** After `DONE`, a signed-out look at `urls.prod` in the built-in browser (`mcp__Claude_Browser__*`) at 375 and 1024 px, on `/` and every route the release adds or changes (the PR's "What changed"): the page loads, the release's change shows, the console has no errors. One screenshot each, nothing clicked past a link. A failed look is a failed smoke: fix forward (step 5). No `urls.prod` (a project that ships nowhere): no look.
7. **The record.**
   - A PR comment, written with Write in the scratchpad and posted with `gh pr comment <n> --body-file <file>`: "Merged and deployed on Alexander's go (/one-ring <argument>)", the run's output from the first line to `DONE` in a code block, every stop and its fix on the way, the backup folder, the look's result, `@<reviewer>` when kit.json names one.
   - **Production memory:** `project_production_migration_pending.md` in this project's memory says what production now has (migrations, functions, date) and the backup folder.
   - **Deploy usage:** `node ${CLAUDE_PLUGIN_ROOT}/scripts/usage.mjs --timeline <this session's id>` (`get_session` with `"self"`), posted as one more PR comment under a "Deploy usage" heading.
   - **Human steps afterwards** (the PR's list): ticked in the ledger `<plans>human-steps.md` as they run (`[x] (<date>)`), walked with him one at a time (norms.md, "A human step"); they never hold the deploy.
8. **The end.** Stop the watchdog and any background task this run started, then the final message: the PR link, what shipped (the `DONE` line), each stop and how it was fixed, the look, the human steps afterwards with the ledger link, the wrap line in the card's voice, and `Next: /future-ted <version> in a new session (Alexander).` A session that another started reports back to it once (norms.md, "Report back").

## check: what the deploy would do, changing nothing
`/one-ring check <version or PR number>` (kit 1.7) is a look, not a go: `one-ring-go.mjs` never reads `check <arg>` as one, so the deploy call stays shut. Run only the reads below, each as its own call, then print one block and stop. Never `gh pr ready`, `gh pr merge`, `gh pr comment`, `full-auto.sh deploy` or `arm`, a backup, a push, a setting or a function deploy; a step that would need one is a line in the block, not a call.
1. **The PR:** `gh pr view <arg> --json number,title,state,isDraft,headRefName,headRefOid,mergeable,body` (a version: the PR whose branch is `V<version>`) and `gh pr checks <n>` for CI on its head.
2. **Its production steps, as the deploy reads them:** `<database>/scripts/full-auto.sh preview <version>` (the script from "The run" step 1; it prints production-steps.mjs's list, what is left off and why, and writes nothing). A PR not on a `V<version>` branch has no preview: say so and quote its "Production steps" section.
3. **Its migrations and functions:** `git fetch origin`, then `git diff --name-status origin/main...<headRefOid> -- supabase/migrations supabase/functions`.
4. **The human steps:** each unticked "Human steps before the deploy can finish", marked "holds the deploy" when tagged `[secret]`, `[password]` or `[payment]` (or naming one), else "listed in a PR comment, carries on".
5. **What production has:** `scripts/prod-db.sh migrations` (a read) for the applied migrations, so the block can say which of the PR's are new. When the guard asks for that read, don't answer it by another route: write "production not read" and go on.

The block: the PR and its CI, the steps the deploy would run in order (out of draft, backup, each migration, each setting, each function, the merge, the host and the smoke), what would hold it, and what production has now. End with `Next: /one-ring <arg> to deploy (Alexander).` A project without a database prints steps 1, 2 and 4 only.

## Projects without a database
The same run. kit.json `"production": "none"` (job-hunt): out of draft, CI green, the squash merge, nothing deploys, no look. `"production": "on-merge"` (portfolio): the same plus the host's deploy, the smoke and the look. **No `production` key and no `refs.prod`** (hejtide's shape): the script stops with setup (2) naming the fix, kit.json `"production": "on-merge"` when `urls.prod` is set, `"none"` when it's empty: a frozen file, so that line goes to Alexander as the one step he does, then `/one-ring` again.

## When the guard asks anyway
The deploy call passes without a prompt when he typed `/one-ring <argument>` in this session in the last 12 hours and the call names the same argument. It asks him once when the argument differs from what he typed or the go is older (a session that sat overnight). In bypass or don't-ask mode, where nothing can be asked, a call without his go is refused: say so in one line and stop. Never re-spell a refused call and never route around it (lesson `[auto]`).
