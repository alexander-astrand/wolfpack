## Pinging Alexander
A ping is a push notification (the PushNotification tool, when it's there) plus a message from `captain-call` saying exactly what's needed and which agent it's about. Ping **only** for:
- a product or scope decision the roadmap entry and CLAUDE.md don't settle (ask with AskUserQuestion, with a recommended option first); it goes to the project's senior adviser first (`yoda`, when the project has one; the kit no longer ships it), per the `oceans-eleven` skill, and then to Alexander (a senior asked for a decision never counts against `stars=`, and the ping names it: `yoda` said …)
- something only a person can do: secrets, the Keychain, dashboard settings, anything on production
  - **A live check handed to Alexander** (a toy run, a QA look, a `--plugin-dir` session) says in three lines what the other window runs, what it may touch outside this machine (or "nothing"), and what to look at and how to stop it (`[live-check]`; in 2.14.8 he had to ask "What exactly am I running in another window?").
- a blocker the Opus escalation couldn't clear, or checks that still fail after a fix attempt
- a must-fix review finding with more than one reasonable fix
- the checkpoint, when asked for
- the end: the draft PR is ready

A look default (a mark, label or placement, however small) goes to Alexander at the start or parks as `TASTE WAIT`, never into the build unasked (`[taste-default]`).

**Every start message, final ping and wrap-up opens with "Not in this release: X → where (agreed when)"**, so nobody has to ask what was left out; a move also goes on the roadmap: the page (`the-trail`), or with kit.json `roadmap: file` the file `<plans>roadmap.md`, where `<plans>` (kit.json `plans`, default `~/.claude/plans/`) holds the release plans, and its `pages.roadmap` page in the same turn (`the-trail`, "The page follows the record"). An option that adds scope is offered as the next release, never "new scope for this one".

Everything else you decide yourself, following CLAUDE.md, and note it in the PR description under "Notes for review". New ideas that come up go on the roadmap with `/badger`, without a ping.

## Where the session ends
The final ping is the end of the autopilot, and of this session's work: once its sends were acted on (`[send-confirmed]`), leave nothing running (norms.md, "Report back": timers, background tasks, Remote Control off), so the wrap can archive this session. Everything after the draft (questions, fixes, live looks, tweak rounds) goes to the **follow-up session** started in the first turn and woken at the final ping (below, "One follow-up session"); a message here after the draft gets one line, "→ <follow-up session>", and no work (`[idle-navigator]`, kit 1.5, H2). His merge go is `/one-ring <version or PR number>`, typed in any session, this one included: that session merges and deploys to the end itself (kit 1.6), the one piece of work this navigator does after the draft; `/skinny-pete` only for a manual or broken case; `/cattle-drive` runs release and deploy on one yes. Afterwards `/future-ted <version>` runs in a new session (Opus, high) to tally usage, review the deploy and set up the next release. The next release starts a new session.
