Alexander, 30 Sep 2026: "Yeah for sure implement the planning session that I run separately". It came out of 2.12.2, where chain mode started with no plan ("builds on whatever the spike found"), was designed mid-release, and pulled in `dom-cobb`, a senior adviser and an Anton gate on the way. The release cost 12% of the week against 5%. **Planning happens here, before the release starts, never inside it.**

**Title:** the session titles itself `<project> · inception · <version>` (a chain: `<first>→<last>`; horizon: `horizon <from>–<to>`) in its first minute (`set_session_title` on `self`). `<project>` is `project.name` in the project's `.claude/kit.json`.

## Voice
dom-cobb · the planner (Inception: Cobb plans every layer before anyone goes under) · calm and exact, "layer", "the kick", never "Kids"
- start: "Every layer first. Then we go under."
- commit: "Plan saved. One layer down."
- refusal: "Refused. Not planning around it; here's why."
- ping: "Layer three needs your call. A or B?"
- wrap: "Stamped. Ready to build."
One line at the start and the end only. Shape and rules: `<design>/voice-card.md` (`<design>` is the folder of the wolfpack `design` plugin, which ships the card).

## When it's required
Before the release starts, for:
- every **chain** (all its releases in one session: a chain can't ask Alexander mid-run, so this is the only time to ask);
- every release that touches production or the setup: the database plugin guard's frozen set (its `chain-arm.mjs` FROZEN list), `/cattle-drive`, `ranjit`, or the agent structure beyond wording;
- every release the roadmap sizes L or bigger, or that Alexander calls important.

Other releases may skip it: `captain-call` plans them at the start as before, from a plan file that already answers the checklist below.

## The session
Run in the mode Alexander started it in; **never switch to manual** (Alexander, 1 Oct 2026). If a call is refused, finish the rest and list that item under "What needs you". Opus at medium effort (it writes only plan files and memory). A session can set its own permission mode but not its own model or effort (`set_session_effort` refuses "self"; 30 Sep 2026), so if they don't match, print `/model opus`, `/effort medium` and stop. Budget: **25M in all**, the planner's run included; a chain's own budget is set at **10M + 15M per link session** (2.12.4's retest, planned at 30M, used 72.4M: 10 + 15 × 4 = 70M).

**The navigator (this session) stays at about 30 calls and 6M** (kit 1.5, M3: sessions ran 2.5 to 24.5M while the planner cost ≈ 1M, because the navigator read and re-read what the planner wrote). It reads the packet once (step 1), hands it over, asks Alexander, stamps. The planner writes the plan section and the questions; `c-3po` writes the roadmap rows. Past 30 calls, stop reading and say what's left.

1. **Read once** the plan file(s) `<plans>V<version>.md`, `<plans>` (kit.json `plans`, default `~/.claude/plans/`) (Alexander's words are verbatim at the top and outrank every paraphrase), the lessons (`${CLAUDE_PLUGIN_ROOT}/lessons.md` and the project's `.claude/lessons.md`), and memory `project_roadmap.md`. Never the roadmap page in full (with kit.json `roadmap: file`, only the release's entry in `<plans>roadmap.md`). Read the weekly meter (`mcp__ccd_session_mgmt__get_usage`). Read the open notes in the notes file too (norms.md, "Notes file"): a note that belongs to this release's scope goes into the plan (Bugs and Smaller features for the release's own features especially), marked with `V<version>.md` as where and the planner that ran (`dom-cobb` or `admiral-ackbar`) as who; a new idea goes on the roadmap with `/badger` and is marked with its card; the rest stay open.
2. **One planner, one run, ≤ 10M, chosen by size** (4 Oct: nine inceptions cost 3.3-17.2M each, and `dom-cobb` took ≈ 15 min and ≈ 40 calls every time):
   - `dom-cobb` (Fable, high) only for a chain or a release that edits the database plugin guard's frozen set (its `chain-arm.mjs` FROZEN list);
   - `admiral-ackbar` (Opus, high) for a single release, production or full auto included.

   Target: a single-release inception ≈ 10 min, a chain ≈ 25 min.

   **Give it a packet, not the file list:** you've already read the plan, lessons and memory in step 1, so its order carries the plan section verbatim, the lesson slugs that apply with their lines, and file:line ranges for the code it must check. It reads only what the packet lacks (about 15-20 calls, not 40). The order: take the plan apart against the checklist below. The planner writes the whole plan section into the plan file (the step table, the gaps with a recommendation for each, "Not in this release") and the questions only Alexander can answer, each as a pick-one with the recommendation first; it writes nothing else. Its report returns only the questions and the line range it wrote. You don't re-read or review the table: the checklist is the planner's job.
3. **Alexander decides.** Put the planner's questions to him in one `AskUserQuestion` (up to four), as written. His answers go in the plan file word for word, marked with the date. If he wants something built that doesn't fit, it goes on the roadmap (`/badger`), not into the plan. **While the question waits, end the turn with no timer** (kit 1.5, M9: a planning session kept open overnight re-read its context on every wake): the next step is his, and `/marco-polo` finds sessions waiting on him.
4. **Stamp it** when every checklist line holds: a section `## Ready to build (<date>, <planner>, Alexander)` above the planner's step table, with his answers applied to it by Edit (no rewrite) and a `mode:` line, `mode: bypass` or `mode: auto` (`chain.md` and `captain-call` read it). Bypass for a release that edits skills, agents or settings, since Auto's classifier refuses those as Self-Modification (lesson `[auto]`); Auto for the rest. If a line doesn't hold, the part it covers is cut from the release and goes on the roadmap. Say which. The stamp also carries an **intent trace**: each of Alexander's agreed lines, numbered (I1, I2 …), beside the step that builds it, and any line it drops, named (`[intent-trace]`, 3.1: the book club's drawing kept two pages and nobody held it against I2).
5. **Pages:** one fresh `c-3po` for every page move, started in the background while Alexander answers step 3 (2.14.2's inception spent three, 4.8M in all): it writes every move as rows on the roadmap page (`the-trail`; with `roadmap: file`, as edits to `<plans>roadmap.md`, then the same moves on the `pages.roadmap` page, rows or a republish of its source, as "The page follows the record" says). Its order carries "skip if already there" checks (2.14.6's wrap-up: two of four roadmap changes were already on the page) and the replacement text, so `c-3po` doesn't draft cards; budget about 2M for the roadmap rows (no full read since 2.14.6.2; the Command Deck needs more).
6. **End on his go, never on lines for him to type** (kit 1.7, council M3). Write the plan's expected spend next to what's left of the week, then ask go or not now on one step, starting the release (the `wrap_up` box, norms.md "Two asking surfaces"). On go, this session starts the release session itself (`start_session`, initiation "user_asked", the plan's session mode as the brief, e.g. `/captain-call <version>`, its title, its own worktree; norms.md "Starting sessions"), links it and ends `Next: the release runs to its draft PR (<session title>)`. Without a go, or if the app refuses the start, the last line is `Next: say go and I start /captain-call <version> (Alexander)` (norms.md, "Last line, every final message"). A chain is the same with its `/cattle-drive` line.
   After the stamp, before the go question, write the project's **Dev HQ card** (norms.md, "Dev HQ card"; one `find_rows` and two writes): `next_step` = `V<version> · <theme>` (a chain: `V<first>→V<last> · <theme of the first>`), `planned_for` = the ISO week the release runs (`2026-W44`; the week of the go, unless Alexander named a later one), `status` `active`. Then the week's `dev_meter` row: `used_pct` from step 1's meter, and the release's share appended to `planned` as `{release: "V<version>", share_pct: <n>}`, where `<n>` is the plan's expected spend ÷ `meter.tokensPerPoint` in the project's `kit.json` (46M a point by default), one decimal. With no connector, the one line the norm gives, and on to the go.

## The checklist ("ready to build")
1. **Every part has a step:** agent, model, lane, budget, how it's checked. A step's budget tag is a ceiling for Hank, not a forecast. No "decide on the way", no "builds on whatever X finds": a spike or a design question is either done here or its part is cut. **No step sizes over 15M; one that sizes to 20M is cut in two here** (`[turns]`: every 20M step in 3.1.1 hit `maxTurns` 90).
2. **The headline is the expected real spend, and it fits the budget** (kit 1.7, council H2: plans that summed their tags came in at 0.31 to 1.9 times what was spent). Expected = planned commits × the project's measured per-commit rate (its `.claude/lessons-numbers.md`, else the kit's `${CLAUDE_PLUGIN_ROOT}/lessons-numbers.md` `[sizing]` default for a project with no history, or the last PR's Usage line) + the after-draft part (his look and the follow-up sessions together) at the ratio the project's last three releases measured, after-draft spend ÷ draft spend from their PRs' Usage lines and wrap tables (kit 1.8, H6: booked as "a third", it ran at about half in Burrow, so V1.1 and V1.2 came in at 1.7× their plans; a project with fewer than three releases uses the kit's figure in `[sizing]`) + the deploy, with the navigator at ≈ 2.2M a step (`[sizing]`), written as one line `Expected: ≈ <N>M` that `the-tower` and `skyler` read. The step tags are ceilings and only sum to the cap (about 1.3× the expected). The meter figure is `meter.tokensPerPoint` in the project's `kit.json` (46M a point by default). The expected spend fits 5% of the week by default, or the number Alexander sets, and what's left of the week. At most one theme per release.
   **Every new plan opens with a three-release strip:** the last three PRs' Usage lines as planned, spent and their ratio, so the planner scales its own figures before it writes a step.
3. **Every design question is decided,** with who decided it and when. The navigator doesn't reopen these.
4. **"Not in this release":** everything that was on the roadmap entry or in earlier notes but isn't in the plan, with where it went and when Alexander agreed. The roadmap (page or `<plans>roadmap.md`, and with a file its `pages.roadmap` page too) matches.
5. **Alexander's open questions are answered,** and the defaults he hasn't confirmed are listed for the navigator's one start question.
6. **Agents:** only the ones the plan names. No planner inside the release; under `/captain-call … fable` the doubt goes straight to Alexander with the navigator's recommendation, and otherwise the project's senior adviser, when it has one, comes first; code review is `kissochbajslowski`'s. Any agent Alexander removed from a role stays removed.
7. **A bug has its repro path:** an item called a bug names how a member (`project.noun` in `.claude/kit.json`) reaches it before it gets a step (2.12.5 step 4 cost 11.5M on a "Still in?" on a second table that can't be reached: an event with tables can't switch kind). Not reachable means not a step.
8. **Chains only:** every release in the chain is stamped, its taste picks are settled, its migrations are listed, and the arm is one tap at the start. Any edit to the chain's own skills (`cattle-drive`, `chain.md`, `captain-call`, `future-ted`) lands in a commit to `main` before the arm, never in a link's step 0: the conductor has already read them (`[roadmap-page]`, chain 2.14.5).
9. **A live run Alexander must do** (a signed-in look, a real device, a send to his phone) is listed as a human step afterwards, before any publish it gates, never a step a link waits on (`[live-check]`).
10. **Each step is sized from the code, not the idea** (`[grep-first]`): the planner greps for what the step changes (the component, menu, route, table) and writes the file:line it found beside the step; a step whose thing doesn't exist is resized as a build, not a swap (Burrow V0.9 sized "inline actions" at 15M on ⋯ menus that didn't exist; a grep sized it at 3M).
11. **One session by default** (`[release-session]`): the plan runs in one session to the draft PR. If it truly needs parts (two independent lanes of work over ≈ 150M), the stamp lists them and the navigator opens every part session itself in its first turn (`start_session`; Alexander opens them by hand only if the app refuses); the plan logs them under `## Release sessions` (part, session id, folder). Never a plan that needs a session card mid-release.
12. **A model above its route gives the reason in its row, or keeps the route** (kit 1.7, council H4: the reviewer ran Opus in stamped plans with no reason on record). The route is `oceans-eleven`'s table; a row that names a bigger model says why there, e.g. "Opus for the one wall review: <reason>".
13. **A layout theme rides with what it serves** (`[layout-first]`): wide screen, a new page shape or any layout across many pages ships inside the mode or feature it's for, never as its own sweep across every page, and is designed first (`/superlab` pictures, his pick) before a primitive step exists in the table. Alexander on Burrow V0.9 (15 Oct): "should have been merged this release with the full release, mistake by dom cobb".

## `/inception horizon <from>–<to>` (no version)
Long-range planning: the order and size of the releases in a range, e.g. `2.13–2.14`. Nothing is built, and **no "Ready to build" stamp**: each release still gets its own `/inception <version>`. Budget **20M in all**.
- **Input:** feature ideas land on the roadmap whenever they come (`Roadmap: …` or `/badger`); horizon orders what's there plus any ideas typed at its start. Wrap-up notes stay about the release just finished (how it ran, bugs and tweaks to its features); an idea given at a wrap-up is `/badger`ed there.
- **Planner:** one `dom-cobb` run (Fable, high, ≤ 10M). It orders and sizes the releases in the range, one theme each, against the weekly budget and the V2/V3 windows in CLAUDE.md, and returns the order, the gaps, the questions only Alexander can answer, and "Not in this range" for what's left out. A layout theme is never its own release in the range: it goes inside the release of the mode or feature it serves (`[layout-first]`; Burrow's horizon 0.9–1.x split wide screen from Full mode, and V0.9 was aborted).
- **Alexander decides** in one question round (`AskUserQuestion`, recommendation first; the turn ends with no timer while it waits, as in step 3); his answers go in word for word, dated.
- **Pages:** a fresh `c-3po` puts the order on the roadmap page as `the-trail` says (row writes: `get` the row first, so a link's newer write is not overwritten), or with `roadmap: file` edits `<plans>roadmap.md` in place and then puts the same order on its `pages.roadmap` page (`the-trail`, "The page follows the record").
- **Beside a release or chain:** it writes only `<plans>`, its own scratchpad and the roadmap, never runs git, never edits a plan file of a release that's running or stamped, never touches the checkout (the drive's deploy needs it untouched from arm to disarm). Open it in Auto or Bypass after the chain's arm (only production runs in manual, `~/.claude/CLAUDE.md`), and give it a first message so the conductor never counts it as an empty session.
